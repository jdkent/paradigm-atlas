## 1. Schema structure

### 1.1 Two schemas, one shape

- **Storage** (`neuroimaging-study-storage.yaml`, v0.7.0) is the normalized, query-oriented
  schema that NeuroStore uses. It is the source of truth and is "never narrowed in place".
  Each attribute carries `in_subset` marks on two independent axes:
  - `mvp`: included in the first production release.
  - `deterministic` or `model_extracted`: filled by code (an API lookup or derivation) or by
    an LLM reading the paper.
- **Extraction** (`neuroimaging-study-extraction.yaml`, v0.5.0) is **generated** from storage by
  pondie (`python3 -m pondie.schema.generate`). It has the same classes, slots and nesting, with
  these mechanical changes:
  - `deterministic` fields are dropped.
  - `id` becomes `local_id`.
  - `string` becomes `ExtractedString`.
  - An enum, or `any_of: [Enum, string]`, becomes `Extracted<Enum>`, keeping the same open or
    closed range.
  - A multivalued field becomes `Extracted<T>List`: one wrapper and one evidence record over
    the whole list.
  - `rules`, `unique_keys` and `minimum_value` are dropped.
- **Evidence wrapper** (`extraction-evidence.yaml`). Every extracted value is an `ExtractedValue`
  with these fields:
  - `extraction_status`: `extracted | not_reported`.
  - `value`.
  - `value_source`: `reported` ("Explicitly stated in the source…") or `generated` ("Created by
    the extraction system; evidence supports the underlying entity or concept").
  - `unreported_reason`: `ambiguous | outside_text | cited_elsewhere | undetermined`.
  - `evidence`: `status` is `present | not_found | not_applicable`, and `sets` holds
    `EvidenceSet`s of spans with `text`, `start_char` and `end_char`. Each set's `source` is
    `model_quote | retriever | literal_match | repair_pass`.
- **Open vocabularies** are the dominant pattern. Most enum slots are declared
  `any_of: [{range: <Enum>}, {range: string}]`, so the field holds either a permissible value or
  the source's own words ("A value outside a vocabulary is a signal for review, not a validation
  failure"). `Modality` is the one exception: it keeps `other`.

### 1.2 Where tasks sit: the three layers (`analysis-entities.md` §1)

| Layer | Classes |
|---|---|
| Entities: what existed in the study | `Group`, `Task`, `Condition`, `Arm`, `Timepoint`, `Region`, `Assessment`, `Acquisition`, `Device` |
| Model: what was fitted | `ModelEstimation`, `ModelTerm`, `FactorLevel` |
| Result: what was tested | `Analysis`, `Effect`, `Cell`, plus `Statistic`, `Measure`, `AnalysisGroup`, `AnalysisDetails`, `InferenceSettings` |

Each layer refers downward by identifier. A condition never reaches a result directly. It
reaches one by being the level of a model term that a contrast put a sign on:

```
Study.tasks[] Task ── conditions[] Condition
                                     ▲
ModelEstimation.terms[] ModelTerm ── levels[] FactorLevel.conditions[]
                                     ▲ (matched by Cell.level == FactorLevel.level)
Analysis.effect Effect ── cells[] Cell{term, level, direction}
Analysis.tasks[] ──► Task           (non-directional context link)
```

Ownership (`analysis-entities.md` §4):

| Class | Declared in | Referenced from | How many |
|---|---|---|---|
| `Task` | `Study.tasks` | `Analysis.tasks` | one per paradigm, resting state included |
| `Condition` | `Task.conditions` | `FactorLevel.conditions` (also `DecodingClass.condition`) | one per modelled state of that task |
| `Acquisition` | `Study.acquisitions` | `Task.acquisitions`, `Analysis.acquisitions` | one per protocol |
| `Assessment` | `Study.assessments` | `ModelTerm.assessment`, `Analysis.assessments` | one per instrument |

### 1.3 `Task`, verbatim (`neuroimaging-study-storage/task.yaml`)

Class description:
> A meaningful participant paradigm, such as a task, resting-state protocol, stimulation, or
> passive viewing, performed in association with an acquisition. A Task record is required
> wherever the study models conditions, a resting-state protocol included. Acquisitions with no
> paradigm do not require one, even in a longitudinal or interventional study: a structural
> comparison across occasions is carried by the Effect's timepoint terms and linked through
> Analysis.acquisitions.

| Slot | Range | Subsets | Review priority | Description (verbatim) |
|---|---|---|---|---|
| `id` | string, identifier | mvp, deterministic | n/a | — |
| `name` | string | mvp, model_extracted | 1 | Short, unique label for the task or paradigm; corresponds conceptually to BIDS TaskName when applicable. |
| `description` | string | mvp, model_extracted | 1 | Complete narrative description of what participants experienced and did. |
| `conditions` | `Condition`, multivalued, inlined_as_list | mvp, model_extracted | 1 | The conditions this task was made of. These are the different states/modes of the task. |
| `design_type` | `any_of: [DesignType, string]` | mvp, model_extracted | 1 | How the task's events were modelled in time. Open vocabulary: write the source's own wording in the field when nothing here fits. |
| `acquisitions` | `Acquisition`, multivalued, by reference | mvp, model_extracted | 1 | The acquisition protocols used to collect data for this task. Exclude structural scans unless they are part of the task itself. |
| `presentation_software` | string | model_extracted | 3 | Stimulus-presentation software name, version, and operating system when reported. |
| `instructions` | string | model_extracted | 2 | Task- or paradigm-specific instructions given to participants. |
| `references` | string, multivalued | mvp, model_extracted | (not in the priorities file) | Works the source cites for this task, exactly as it writes them: an author-year citation or a bracketed reference number, kept in the source's own punctuation. Copy the in-text citation; do not resolve, expand or look it up. Multivalued -- a task may cite the paradigm's origin, an adaptation, and the stimulus set separately. Empty when the source cites nothing for the task. |
| `stimuli` | string, multivalued | model_extracted | 1 | The materials presented to participants, in the source's own terms -- the stimulus set, its name, how many items. One entry per distinct material; `stimulus_modality` carries the sensory channel. |
| `stimulus_modality` | `any_of: [StimulusModality, string]`, multivalued | mvp, model_extracted | 1 | The sensory channel the stimuli were delivered through. Multivalued because a paradigm may use more than one -- a photograph with a spoken label. Often not stated in those words: a source naming IAPS, NimStim, Ekman faces or film clips has said `visual` without using the word. Inferring it from such a cue is intended, and the cue is what belongs in the evidence -- not the whole methods section. |
| `response_modality` | `any_of: [ResponseModality, string]`, multivalued | mvp, model_extracted | 1 | How participants responded. Multivalued because a paradigm often collects more than one -- a button press for accuracy and a spoken report afterwards. |
| `performance_measures` | string, multivalued | model_extracted | 1 | Behavioral variables recorded and summaries used to verify task performance. |

### 1.4 `Condition`, verbatim

Class description:
> A named condition of a task: a modelled state, event type, or baseline that an analysis can
> contrast against another. Only what happened inside the paradigm -- the occasion the task was
> run on and the arm it was run under are Timepoints and Arms, and enter an analysis as levels of
> their own model terms, compared by `Cell`s on the Effect.

| Slot | Range | Subsets | Description (verbatim) |
|---|---|---|---|
| `id` | string, identifier | mvp, deterministic | Stable identifier. |
| `name` | string, **required** | mvp, model_extracted | Short condition label that distinguishes the condition from other task periods or modeled effects. |
| `stimulus_content` | string, multivalued | mvp, model_extracted | What this condition's stimuli were about -- their category, not the channel (`Task.stimulus_modality`) or the materials (`Task.stimuli`): a cigarette photograph is `cigarettes`. Faces, scenes, words, tones, music, food, money -- examples, not a vocabulary. Leave unset where the stimulus does not distinguish this condition from the others: every n-back load level shows the same letters. |
| `condition_kind` | `any_of: [ConditionKind, string]` | mvp, model_extracted | What kind of state this was: an active task state, a rest or fixation period, or a state the source calls a control or neutral condition. A field of its own rather than a phrase in `description`, which a consumer cannot reliably read it out of. |
| `description` | string | mvp, model_extracted | Complete definition of the condition, including whether it put a demand on the participant. Whether it was a rest, fixation, or control state belongs in `condition_kind`. A rest or fixation period inside another paradigm is a Condition of that paradigm's Task. A standalone resting-state run is not: it is its own Task, with one condition or none. The distinction is which paradigm the participant was in, not what they were doing -- a fixation baseline between working-memory blocks belongs to the working-memory Task. What a tested effect was measured against is not recorded here: a contrast against this condition gives it a `negative` cell, and a contrast against the unmodelled implicit baseline has no second cell. |

(`storage-parameter-priorities.yaml` lists only `Condition.name: 0` and
`Condition.description: 0`. `stimulus_content` and `condition_kind` have no entries yet. That is
drift, and the unmerged branch adds them.)

### 1.5 Contrasts: how conditions are compared

There is **no contrast class keyed by condition names**, and no `baseline` field. A contrast is:

- **`Analysis`**: "A distinct reported inferential map or tested effect". It holds:
  - `name` and `definition` (required): "Precise statement of the tested effect in the source's
    own words…".
  - `interpretations`: Results/Discussion sentences, verbatim.
  - `prespecification`.
  - `tasks`: `Task`, multivalued, by reference. Described as "The participant paradigms that
    contextualize this analysis. An analysis can span paradigms, as a cross-task conjunction or
    a localizer-plus-main-task analysis does. A resting-state analysis names its Task here like
    any other…".
  - `acquisitions`, `groups` (`AnalysisGroup`: membership and n), `measure`,
    `model_estimation`, `effect` and `details`.
- **`Effect.cells`** (required, non-empty): "What this contrast compared: one entry per level of
  a model term that entered it, each with the side it sat on. The only place direction lives."
- **`Cell`**: `term` (a `ModelTerm` reference, required), `level` (string, which must match a
  `FactorLevel.level`), `direction` (`Direction`, required) and `label` (the source's wording).
- **`ModelTerm`**: `name`, `type` (`categorical | continuous`), `levels`, `assessment`,
  `region`, `variation_level`, `functional_form`, `interaction_with`, `unit` and
  `source_definition`.
- **`FactorLevel`**: `level`, `order` and five entity slots: `conditions`, `groups`,
  `timepoints`, `arms` and `regions`. "A factor normally ranges over one of the five --
  conditions for a task factor, cohorts for a participant factor… A factor whose levels are not
  entities of the study at all -- hemispheres, **tasks**, frequency bands, acquisition sessions
  -- leaves all five empty and is carried by `level` alone."
- **`Effect.kind`** (`EffectKind`, closed) is stated by the extractor and also derived from the
  cells. A mismatch flags the record.

Baseline routing (`extraction-readme.md` §3):

| the paper says | where it goes |
|---|---|
| rest, fixation, a control task | a `negative` cell on that condition's level |
| the implicit baseline, or zero | no second cell -- the lone signed cell *is* the test against zero |
| chance, chance level | `PerformanceMetric.reference_value`, per metric |
| "versus baseline", unspecified | whatever cells the contrast yielded; the vagueness stays in the evidence |

Ordered contrasts such as parametric load: "For an ordered comparison mark the extremes
`positive` and `negative`, leave the levels in between out of `cells`… and keep the ordering on
`FactorLevel.order`." ModelTerm naming: "A paper reporting 1-back, 2-back and 3-back conditions…
frequently names no axis; `load` is then a name supplied for a grouping the source does make.
That is permitted, within two limits: the levels must be source-stated, and the name must not
assert a comparison or a construct the paper does not."

Other task-adjacent slots:

- `DecodingClass.condition` (`analysis_details.yaml`): "The experimental condition this class
  corresponds to, when it is one."
- `TablePurpose.stimulus_or_task_list`: "The stimuli, conditions or trial structure of the
  paradigm."
- `ResultKind.contrast`: "Conditions, groups or tasks compared (A > B, patients > controls)."
- `MeasureType.bold_response`: "BOLD activation, task activation, or task-evoked response."
- `ModelEstimation.hrf_model` is free text.
- `Assessment` is separate from `Task`. It is "A behavioral, cognitive, biological, clinical, or
  questionnaire-based instrument or procedure that produces participant-level measurements
  independently of the neuroimaging acquisition or experimental conditions". It has `name`,
  `description` and `assessment_type` (free text: "cognitive test, clinical scale, diagnostic
  interview, questionnaire, behavioral task, …"). An out-of-scanner Digit Span is an Assessment.
  An in-scanner paradigm is a Task.
- `StudyDesign`, `Arm` and `Timepoint` (`design.yaml`) cover between-session manipulations
  (drug, stimulation, training) and occasions. They are **not** part of the task. A
  drug-vs-placebo factor is a `ModelTerm` whose levels name `Arm`s.
- `Study.hypothesis`: the verbatim predictions.

### 1.6 Unmerged branch: paradigm normalization (`origin/claude/gallant-shannon-dhsj8u`, 2026-10-09)

This branch is the most relevant work to the taskCategories project. It adds the following to
`Task`, verbatim from the branch's `task.yaml`.

`paradigm` (string; mvp, model_extracted; priority 0):
> The name with every qualifier that says how this version varies taken off and moved to its
> own field: `Stroop task` for an emotional Stroop task, `flanker task` for an auditory flanker
> task, `n-back task` for a food-picture n-back, `incentive delay task` for a monetary incentive
> delay task. The same as `name` when nothing qualifies it. This is the extractor's split, made
> the same way in every paper. Whether the stem or the qualified name is the paradigm is not a
> fact one paper can state; it is decided across the corpus, in `paradigm_category`.

`paradigm_category` (string; mvp, **deterministic**):
> The paradigm this task is grouped under, decided by task normalization across the corpus
> rather than read from one paper. The stem in `paradigm` when the corpus shows it varied --
> `Stroop task` once an emotional, a counting or an auditory Stroop appears beside it -- and the
> qualified name when that variant is the only form ever seen. Citations sharpen the call: tasks
> whose `reference_ids` lead back to the same originating paper belong to one lineage. An
> outside vocabulary such as the Cognitive Atlas is a noisy suggestion, filtered against the
> corpus, never the authority on which variants are paradigms.

`reference_ids` (string, multivalued; mvp, deterministic):
> `references` resolved to the works they cite, as DOIs or PMIDs, through the parsed paper's
> reference list. What links a task to the paper that introduced it and to the adaptations that
> cite it, so a task's lineage can be followed.

`variant_qualifiers` (`TaskQualifier`, multivalued; mvp, model_extracted):
> The words of `name` that `paradigm` leaves out, each with the axis it varies the paradigm on.
> Each is also stated in its own field: a stimulus-content qualifier in `stimulus_content`, a
> modality qualifier in `stimulus_modality` or `response_modality`, a timing qualifier in
> `design_type`. Empty when `paradigm` equals `name`.

`stimulus_content` (task-level; string, multivalued):
> What the task's stimuli were about when that holds across all its conditions -- food pictures
> at every n-back load, emotional words throughout a Stroop -- which `Condition.stimulus_content`
> leaves unset because it does not tell the conditions apart. The task-level half of the
> stimulus facet: a meta-analysis can ask for food stimuli across paradigms, or for Stroop tasks
> across stimuli, without either question splitting the other.

`TaskQualifier` has two slots:

- `qualifier`: "The qualifier as the name prints it" (required).
- `axis`: `any_of: [TaskVariantAxis, string]`, "What the qualifier varies" (required).

`TaskVariantAxis` (open) values:

| Value | Description |
|---|---|
| `stimulus_content` | What the stimuli are about -- emotional, food, alcohol, numerical, face. |
| `stimulus_modality` | The sensory channel -- auditory, visual, tactile. |
| `response_modality` | How the subject answers -- vocal, manual, saccadic. |
| `design` | How events are timed -- block, event-related, rapid, mixed. |
| `adaptation` | A modified or shortened version, or one adapted for a population -- modified, child-friendly, short, computerized. |

The map on that branch says `paradigm_category` "Set by pondie's task normalization over the
whole corpus, not per record". `reference_ids` is resolved through
`neuroimaging-paper-parse` `ParsedPaper.citations`, by overlapping the task's evidence spans.
Heuristic alignments count only above a threshold.

### 1.7 Ontology linkage: none by design

The storage schema description, verbatim:
> No field in this schema binds a subject-matter vocabulary, and none stores a cognitive
> concept, construct, or domain. Values are the source's own wording; mapping them onto ONVOC,
> Cognitive Atlas, MeSH or an anatomical vocabulary is a later stage that reads the free text
> and its evidence sentences. onvoc-mapping-audit.md records which fields that stage can map and
> which facets have no field to map.

The `see_also` list includes `https://www.cognitiveatlas.org/`, `https://w3id.org/onvoc/`,
`https://brainmap.org/taxonomy/`, `https://pmc.ncbi.nlm.nih.gov/articles/PMC3682219/` (CogPO),
COBIDAS, ReproSchema, BIDS and BIDS Stats Models. These are design references only. **No slot
has a CURIE range, `meaning:` mapping, `exact_mappings` or ontology prefix.** **HED does not
appear anywhere** in the schema or its docs.

The only explicit vocabulary borrowings:

- `ResponseModality.covert_response`: "CogPO's covert response: real, instructed, and
  unobservable, so no accuracy comes with it."
- `ResponseModality` as a whole merges BrainMap's Response Modality and Response Type (probe
  F23).
- `Task.name` is "conceptually" BIDS `TaskName`.

## 2. Task-related controlled vocabularies, verbatim

All four task enums are **open** (`any_of: [Enum, string]`) and in `mvp`.

### `DesignType`
> How a task's events were modelled in time -- not what the task was or what it showed.

| value | description |
|---|---|
| `block` | Conditions presented in extended runs of like trials and modelled as those runs. Covers `blocked`, `block design` and a randomised or alternating block order: randomisation is how the blocks were sequenced, not a different design. |
| `event_related` | Individual trials modelled as separate events. Rapid, slow and fast variants are this design at different inter-stimulus intervals; write the source's phrase in the field when that distinction matters. |
| `mixed` | Both in one run -- events modelled within blocks that are themselves modelled. Only where the source says it used both, not where a block design happens to have trials. |
| `continuous` | No discrete events modelled: resting state, film or music played through, naturalistic viewing. The task ran continuously and the analysis is of that run. |

### `StimulusModality`
> The sensory channel a task's stimuli were delivered through.

| value | description |
|---|---|
| `visual` | Anything seen -- photographs, faces, scenes, words on a screen, film clips, gratings, a fixation cross. The commonest modality in the literature by a wide margin, and the one a named stimulus set usually implies. |
| `auditory` | Anything heard -- speech, tones, music, environmental sounds, noise bursts. |
| `tactile` | Touch or somatosensory delivery -- brushing, vibration, pressure, temperature, electrical or noxious stimulation of the skin. |
| `olfactory` | An odour delivered to the nose. |
| `gustatory` | A taste delivered to the mouth -- sucrose, quinine, juice, a tasteless control. |
| `interoceptive` | A stimulus acting on internal state rather than an external sense -- gastric or bladder distension, inspiratory load, infusion, induced hunger or thirst. |
| `none` | A positive assertion that no stimulus was presented -- resting state, or a task driven entirely by instruction or self-generated thought. Not the same as leaving the field empty, which says nobody looked. |

### `ResponseModality`
> How participants responded during a task.

| value | description |
|---|---|
| `button_press` | A discrete report on a button box, keypad, keyboard, joystick, or mouse. The commonest response in the literature by a wide margin. |
| `hand_movement` | A hand or arm movement that is itself the response rather than a report -- finger tapping, a sequence, grasping, reaching, writing, drawing. |
| `speech` | An overt vocal response -- naming, reading aloud, answering, generating words. |
| `covert_response` | A response made silently and not emitted -- covert naming, subvocal rehearsal, imagined movement, counting to oneself. CogPO's covert response: real, instructed, and unobservable, so no accuracy comes with it. |
| `eye_movement` | A saccade, antisaccade, smooth pursuit, fixation shift, or instructed blink. |
| `foot_or_leg_movement` | A pedal press, foot or toe tapping, or ankle or leg movement. |
| `oral_nonspeech` | A mouth or airway action that is not speech -- swallowing, chewing, tongue or jaw movement, a breath hold. |
| `none` | The task required no response: passive viewing or listening, film watching, resting state. A positive statement, and not the same as leaving the field empty. |

### `ConditionKind`
> What kind of state a condition was, in itself. … Intrinsic to the condition and not its role
> in any one contrast. What a tested effect was measured against is carried by `Cell.direction`,
> which a contrast fills for each side; a condition can be the comparator in one analysis and
> the target in another, and recording that here would make it a property of the wrong thing.

| value | description |
|---|---|
| `task_state` | An active state the paradigm put the participant in -- viewing cues, performing a trial, responding. The default, and the one most conditions are. |
| `rest` | A period with no task demand, in which the participant was asked only to rest. A rest block inside another paradigm; a standalone resting-state run is its own Task. |
| `fixation` | A period spent fixating a cross or point, with no other demand. Distinguished from `rest` because papers report them separately and use them differently. |
| `control_state` | A state the source itself calls a control, neutral, or comparison condition -- matched to the state of interest on everything but the manipulation. Recorded because the source labelled it so, not because a contrast used it that way. |

### Contrast-side vocabularies (value names only; full text is in `analysis_enums.yaml`)

| Enum | Values | Open/closed |
|---|---|---|
| `Direction` | `positive`, `negative`, `undirected` (F/χ² with no per-level sign), `held` (the level a contrast was taken *within*, e.g. "patients vs controls, in the task condition") | closed |
| `EffectKind` | `simple_effect`, `contrast`, `interaction`, `parametric_modulation`, `cross_subject_regression`, `omnibus` | closed, no free-text branch |
| `TermType` | `categorical`, `continuous` | closed |
| `VariationLevel` | `within_subject`, `between_subject`, `mixed` | open |
| `Prespecification` | `preregistered`, `exploratory` (and `planned` on GitHub main) | open |
| `Modality` (acquisition) | `fMRI`, `sMRI`, `dMRI`, `MRI`, `EEG`, `fNIRS`, `PET`, `MEG`, `SPECT`, `other` | closed + `other` |
| `ArmKind` (design) | `pharmacological`, `stimulation`, `behavioural_intervention`, `placebo`, `sham`, `active_comparator`, `usual_care`, `no_intervention` | open |
| `AssignmentStructure` | `observational_cohorts`, `parallel`, `crossover`, `within_subject`, `single_group` | open |
| `TimepointRelation` | `pre_intervention`, `during_intervention`, `post_intervention`, `single_occasion`, `not_applicable` | open |
| `TaskVariantAxis` (branch only) | `stimulus_content`, `stimulus_modality`, `response_modality`, `design`, `adaptation` | open |

## 3. Design decisions about tasks, and why

| Decision | Where recorded | Reasoning |
|---|---|---|

## 5. Gaps: task features not represented that matter for querying and categorizing

### A. Cognitive and ontological identity (the largest gap, and deliberate)

1. **No task-class or paradigm identifier.** No Cognitive Atlas task ID, CogPO paradigm class,
   BrainMap paradigm class or HED tag exists. `Task.name` is free text. The unmerged
   `paradigm` / `paradigm_category` fields are the first step, but they are corpus-derived
   strings, not ontology terms.
2. **No cognitive construct, process or domain** at any level (task, condition or contrast).
   This is refused by design, and concepts are to be derived from `Analysis.interpretations`.
   A task-categorization schema needs to decide whether to hold these and at which level.
   Constructs differ between a task and its contrasts: n-back vs 0-back taps working memory,
   while 2-back vs fixation adds visual processing.
3. **No contrast-level semantics.** Nothing says what a contrast is supposed to isolate. The
   cells state the arithmetic, but not "this isolates inhibition".

### B. Stimulus features

4. `stimulus_content` is **free text with no vocabulary** ("Faces, scenes, words… examples, not
   a vocabulary"), and wording is inconsistent in practice.
5. There are no stimulus properties beyond the channel and the topic. Missing:
   - valence and arousal (emotional vs neutral is only implicit in condition names);
   - semantic category hierarchy;
   - format (static image, video, text, tone, speech; real vs synthetic);
   - social vs non-social content;
   - self-relevance;
   - novelty or familiarity;
   - number of items and repetition;
   - duration, ISI, SOA, jitter;
   - stimulus set identity as a normalized ID. IAPS, NimStim and Ekman are only strings in
     `stimuli`.
6. **Stimulus and response laterality** (BrainMap's dimension) is explicitly not recorded,
   along with which hand, which visual field, monaural vs binaural, and so on.
7. **Per-condition modality** is missing. Modality is task-level only, so cross-modal paradigms
   (auditory vs visual conditions in one task) cannot say which condition is which except in
   `description`.

### C. Response and instruction features

8. There is no **response type or judgment** as distinct from the effector. Examples: detection,
   discrimination, categorization, recognition, recall, rating, choice, go/no-go withholding,
   free report. BrainMap's Response Type and CogPO's Instruction class have no structured slot.
   `instructions` is prose.
9. Missing: **number of response alternatives**, speeded vs unspeeded, feedback (present or
   absent, contingent, monetary), reward or incentive structure, and response deadline.
10. `performance_measures` is free text. There is no behavioral results field (RT or accuracy
    values, or whether a behavioral effect was found) to check task validity.

### D. Design and timing

11. There is **no event timing**: trial and block durations, number of trials and runs, ISI,
    jitter, total task duration, or counterbalancing. `standards-crosswalk.md` names this
    explicitly. `DesignType` has four coarse values. Rapid vs slow event-related designs and
    the naturalistic vs resting split within `continuous` are only recoverable from free text.
12. **Factorial structure is not a property of the task.** Crossed manipulations (valence ×
    probe in 4b) appear only as `ModelTerm`s on a model. A task with no reported analysis over a
    factor loses its factor structure. There is no `Task.factors` / `TaskFactor` (manipulated
    variable plus levels plus which conditions realize each level), and no
    within-task/between-task manipulation type (parametric, categorical, or which dimension was
    manipulated).
13. **Parametric or load manipulations** are recoverable only via `FactorLevel.order`, and only
    when a model term was extracted.
14. **Condition roles** are not recorded: target vs non-target, standard vs deviant, cue vs
    probe vs feedback phase, or trial phase (encoding / maintenance / retrieval; anticipation
    vs outcome). `ConditionKind` has only `task_state | rest | fixation | control_state`, and
    extractors already wrote "passive viewing" and "passive listening" because no value fit.
15. **Task-level factors cannot be joined to Task entities.** `FactorLevel` has
    `conditions/groups/timepoints/arms/regions` but no `tasks`. A "group × task" or cross-task
    contrast holds the task only as a level string.
16. **Session context.** `Task.acquisitions` exists, but there is nothing about practice or
    training before scanning, in- vs out-of-scanner administration, or online vs offline
    stimulation.

### E. Provenance and lineage

17. `references` holds raw citation strings. Resolution to DOI/PMID (`reference_ids`) exists
    only on the unmerged branch.
18. Missing: an **adaptation relationship** (task X modified from Y), a population-adapted
    version (child-friendly), and language of materials. Only the branch's `adaptation`
    qualifier axis touches this.

### F. Review hygiene

19. The priorities file lacks `Task.references`, `Condition.stimulus_content` and
    `Condition.condition_kind` on the local/main branch. The tutorial's Condition chapter is
    stale. The design-notes section "Conditions belong to a task" is cited but unwritten.

### 6.3 What pondie does

The README describes it as: "Extract a queryable record of what a neuroimaging paper reports,
normalize its wording onto shared values, and select the subset a meta-analysis should pool."
It has three packages:

- `pondie.extraction`: papers to validated records.
- `pondie.normalization`: a record's wording to shared values.
- `pondie.query`: records to the subset a meta-analysis should pool.

Supporting layers are `pondie/schema/` (reader, authoring, `generate`, `checks`),
`pondie/formats/`, `pondie/vocabularies/` (ONVOC, MONDO, abbreviations) and
`pondie/benchmark/`.

- **Schema used:** the generated `neuroimaging-study-extraction` schema from the submodule.
  `--structured-outputs` decodes under a strict JSON schema generated from it.
- **Stages:**
  1. `tables`
  2. `prose`
  3. `split`: deterministic.
  4. `single`: the whole record in one LLM call, shown the stage-1 table parse listing.
  5. `fill`: open slots, filled round by round.
  6. `evidence`: quotes, or indexed sentence numbers.
  7. `build`: deterministic fixes, PubMed `language`/`study_type`, offset resolution,
     validation.
  8. `repair`: model proposals behind deterministic guards.
- **Run:**
  `pondie extract --pmids papers.pmids --run v3 --model <model> --env .env`. Add `--plan` to
  spend nothing, `--backend codex` to send calls through `codex exec`, and `--stage-model
  STAGE=MODEL` to use a model per stage. Output goes to `data/runs/<name>/`.
- **Schema regeneration and checks:** `python3 -m pondie.schema.generate [--check]`,
  `python3 -m pondie.schema.checks.{linkml,field_provenance,extraction_to_storage_map,storage_parameter_priorities}`.
- **Models:** any OpenAI-compatible gateway (`GatewayCaller`, using `OPENAI_API_KEY` and
  `OPENAI_API_GATEWAY`) or Codex. The 2026-10-08 100-paper pilot used **`gpt-6-astra`** at
  medium effort, with schema commit `74da550` and code commit `1a11442`. 83 of 100 records had
  no validation errors. **NuExtract**: `docs/serving-the-proposer.md` describes `repair`
  proposing with NuExtract 3 (`vllm serve numind/NuExtract3-W4A16`), and
  `scripts/nuextract_recall.py` exists. However,
  `pondie/extraction/repair/propose_with_extractor.py` says the local NuExtract arm "is gone,
  and this is now the only proposer": repair now uses the extraction model itself. NuExtract
  is historical.

### 6.4 pondie's task normalization (directly relevant prior work)

- `pondie/normalization/task.py` (`python -m pondie.normalization.task --out data/task-facets`)
  runs three steps:
  - **seed**: match task names against a normalized Cognitive Atlas task list
    (`normalization/atlas.py`: 856 labels reduced to 639 seeds).
  - **cluster**: group the unmatched tasks by agglomerative clustering over six separate
    similarity channels:
    - `name` (MiniLM);
    - `prose` (description + instructions);
    - `setting` (stimuli + design_type + response_modality);
    - `measures` (performance_measures);
    - `conditions` (a soft set overlap of condition names);
    - `prose_lex` (TF-IDF).
  - **label**: attach the stimulus from `Condition.stimulus_content` as its own column.
- Grain: "One group per **paradigm**, not per variant". Variants (stimulus content,
  modality, load) are attributes. There is a second `family` level for constructs, e.g.
  go/no-go with stop-signal as inhibition.
- Results (`docs/task-categories.md`): 184 categories over 1,672 tasks, 61 named by the
  Cognitive Atlas, 142 tasks unclustered. Coverage: the Cognitive Atlas names a paradigm for
  29% of mentions and ONVOC for none.
- Docs:
  - `docs/task-condition-normalization.md`: neither task nor condition names should be flat
    vocabularies. Curate the **contrast** as a target plus a baseline. Only 21% of cells reach a
